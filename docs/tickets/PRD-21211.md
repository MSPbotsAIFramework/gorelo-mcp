## Product design

### Goals / Non-goals

**Goals**

- Ship a first version of `MSPbotsAIFramework/gorelo-mcp` that gives an agent the core PSA
  capabilities a Gorelo-using MSP would want an AI assistant to read and act on: service desk
  tickets (read, create, comment), clients and contacts, billing contracts, time tracking (read
  and log), and the managed-device (RMM) asset inventory Gorelo exposes alongside its PSA data
  (Gorelo markets itself as a combined PSA/RMM platform — `gorelo.io/blog/how-to-switch-your-psa-
  rmm-to-gorelo`).
- Match the connector contract every other MSPbots vendor MCP follows: Streamable HTTP, stateless,
  credentials read only from request headers, structured `{error:{code,message,retryable}}`
  envelope, cursor-based list paging surfaced consistently (see Data & API contract — Gorelo's own
  pagination is cursor-based, unlike Kaseya BMS/HaloPSA's offset paging, so the envelope shape
  here is adapted to that, not copied verbatim).
- Tool names, descriptions and semantic hints (`readOnlyHint`/`destructiveHint`) follow SOP §A4 so
  the connector is immediately usable to an agent without reading Gorelo's own docs.

**Non-goals**

- **Not a 1:1 port of the 174-operation Gorelo API or the 112-tool open-source reference.** First
  version stays at or under the SOP's 20-tool ceiling (§A4); billing write operations (invoices,
  payments, product catalog), documents/structured-documents, forms, projects, organization
  (users/roles/API keys), and alerts are left out of v1. Each is a straightforward addition later
  against the same OpenAPI document — none require a different auth model or architecture.
- **No destructive (DELETE) tools in v1.** SOP §A4 defaults new tools to read-only and requires
  write/delete tools to justify business necessity with a specific resource id, never a vague bulk
  operation; none of the "delete a ticket", "delete a client", "delete a contract" operations have
  a stated need in this ticket.
- **No asset *patch management* detail (installed patches, pending Windows updates, installed
  apps, hardware inventory) or uptime-monitor management in v1.** These exist in Gorelo's Assets
  tag (`GET /v1/assets/agents/{id}/patches`, `/patches/available`, `/apps`, `/hardware`,
  `/v1/uptime`) but are RMM depth beyond "PSA connector"; the asset list/get tools below cover
  device inventory, which is what a PSA-focused ask needs.
- **No scripts, asset types/tags, or monitoring-policy administration** (`/v1/scripts`,
  `/v1/assets/types`, `/v1/assets/tags`, `/v1/assets/policies`) — configuration surfaces, not
  service-desk/CRM/billing data an agent would read or act on day to day.

### Acceptance criteria

- **AC1** — Given valid Gorelo credentials and no filters, when the caller invokes
  `gorelo_list_tickets`, then it gets up to `limit` (default 50, max 200) tickets — id, display
  number, title, status, priority, type, client, contact, lead assignee, created/updated
  timestamps — with `{items, has_more, next_cursor, total_count}` paging (see Data & API
  contract).
- **AC2** — Given `gorelo_list_tickets` is called with `status_names` and/or `priority_names`
  (comma-separated human-readable names, e.g. `"New,In Progress"` / `"Urgent,High"`), when a name
  does not resolve to a known status or to one of the five fixed priority levels, then the tool
  returns an `invalid_argument` error naming the known values, the same pattern
  `kaseya_bms_create_ticket` already uses in the sibling repo.
- **AC3** — Given a valid ticket id, when the caller invokes `gorelo_get_ticket`, then it gets the
  full ticket record (title, description, status, priority, type, source, client/contact/location,
  lead + assisting assignees, tags, linked assets, created/updated/closed timestamps).
- **AC4** — Given an unknown ticket id, when the caller invokes `gorelo_get_ticket`,
  `gorelo_get_client`, `gorelo_get_contact`, `gorelo_get_contract`, or `gorelo_get_agent_asset`,
  then each returns a `not_found` error envelope, never an uncaught exception.
- **AC5** — Given a valid ticket id and a comment body, when the caller invokes
  `gorelo_add_ticket_comment` with no `conversation_id`, then the comment is posted to the
  ticket's main Public conversation and the tool returns the created comment's id; given a
  `conversation_id` from a prior side-conversation or approval, the comment is posted into that
  conversation instead (Gorelo requires `ConversationId` for those two kinds — see Data & API
  contract).
- **AC6** — Given `title`, `client_id`, `status_name` (or id), `type_name` (or id), and
  `group_id`, when the caller invokes `gorelo_create_ticket`, then a ticket is created and the
  tool returns its id and display number; omitting any of `title`/`status`/`type`/`group_id`
  returns an `invalid_argument` error naming the missing field (Gorelo requires `Title`,
  `StatusId`, `TypeId`, `GroupId`; see Data & API contract).
- **AC7** — Given `gorelo_list_clients`, `gorelo_list_contacts`, or `gorelo_list_contracts` is
  called with no filters, when there are records, then each returns up to `limit` records (default
  50, max 200) with the same `{items, has_more, next_cursor, total_count}` envelope as AC1; given
  a `query` keyword filter, only records whose vendor-searchable fields match are returned (per
  Gorelo's own `Query` parameter semantics for that list — see Data & API contract for which
  fields each `Query` matches).
- **AC8** — Given `gorelo_list_time_entries` is called with any of `client_ids`, `ticket_ids`,
  `user_ids`, `started_since`/`started_before`, then it returns matching time entries (ticket id,
  user, started/ended timestamps, actual hours, billable status, comment), paged the same way as
  AC1/AC7.
- **AC9** — Given a ticket id, `started_on`, and either `ended_on` or `actual_hours`, when the
  caller invokes `gorelo_log_time_entry`, then a time entry is created against that ticket and the
  tool returns its id; given neither `ended_on` nor `actual_hours`, the tool returns an
  `invalid_argument` error (Gorelo requires exactly one way to express duration — see Data & API
  contract).
- **AC10** — Given `gorelo_list_agent_assets` is called with no filters, when there are managed
  devices, then it returns up to `limit` devices (id, name, display name, status, client,
  created/updated timestamps), paged the same way as AC1; `gorelo_get_agent_asset` on a valid id
  returns the full device record.
- **AC11** — Given no Gorelo credentials are attached to the request (missing `X-Gorelo-Api-Key`
  or `X-Gorelo-Region`), every tool returns the existing `not_configured`-shaped `401` at the
  transport/middleware layer (SOP §3.2), never a per-tool exception.
- **AC12** — Given the upstream Gorelo API returns `401`, `403`, `404`, `429`, or `5xx`, each tool
  maps it to the fixed envelope vocabulary (`unauthorized`, `unauthorized` for a wrong-scope `403`,
  `not_found`, `rate_limited`, `upstream_error` respectively) and includes Gorelo's own `Message`
  and 6-digit `Code` from its `Notifications`/`Error` body, never raising an uncaught exception.
- **AC13** — `tools/list` on the deployed server lists all tools from the Tools table below (name,
  description ≤ 500 chars / first line ≤ 100 chars, `readOnlyHint`/`destructiveHint` set per SOP
  §A4), and the server's `instructions` text names the main entities (tickets, clients, contacts,
  contracts, time entries, assets) so an agent can discover them from one call.

### Open questions

- [non-blocking] Should a v2 add billing (invoices/payments) and project tools, matching the open-source
  reference's breadth? — Not blocking: the ticket names no specific capability beyond "PSA" and
  "live access"; v1 covers the service-desk/CRM/time/asset core every sibling PSA connector in
  this org ships first (Kaseya BMS, HaloPSA). Billing and projects are natural v2 additions against
  the same OpenAPI document, filed as follow-ups in Risks & dependencies.
- [assumed] Which Gorelo region (US `api.usw.gorelo.io` vs Australia `api.aue.gorelo.io`) a given
  tenant is on is not stated anywhere in Gorelo's docs as auto-detectable from the API key alone —
  assumed the credential header set must carry the region explicitly, the same shape
  `kaseya-bms-mcp`'s `X-Kaseya-BMS-Tenant-Subdomain` uses to pick a regional host. If a given
  Gorelo tenant's key only works on its own region's host (confirmed by the two separate Swagger
  docs existing per region), a wrong region returns `401`/`403` from Gorelo and the tool surfaces
  it as `unauthorized` — no silent misrouting. If this assumption is wrong (e.g. one global host
  with implicit routing), Data & API contract's header table is the only part that needs to
  change.

## Tech design

### Conclusion

Build `gorelo-mcp` from scratch (SOP main line A — first version of a brand-new MSPbotsAIFramework
repo) as a Python 3.12 + `uv` + FastMCP Streamable HTTP service, structured exactly like
`kaseya-bms-mcp` (most recently built sibling, same "PSA connector, cursor/offset list tools,
structured error envelope" shape): one `tools/<area>.py` module per entity group, a shared
`api_client.py` for the Gorelo HTTP calls with the vendor's cursor-pagination semantics preserved,
and `config.py`/middleware carrying the two credential headers through `contextvars`. The only
structural difference from `kaseya-bms-mcp` is the paging envelope: Gorelo's API is cursor-based
(`Cursor`/`NextCursor`/`HasMore`/`TotalCount`), not offset-based (`top`/`skip`), so tools surface
`cursor`/`next_cursor`/`has_more` rather than `skip`/`next_skip` — this is a vendor API fact, not a
style choice, and is called out explicitly so dev does not silently "fix" it to match the sibling.

### Data & API contract

**Authentication headers** (request headers, SOP §3.1 — one field per header, `X-Gorelo-*`
namespace so it cannot collide with Gorelo's own `X-API-Key` header name):

| Header | Required | Meaning |
|---|---|---|
| `X-Gorelo-Api-Key` | Yes | A Gorelo API key (Settings → Integrations → cog icon → Generate New Key). Sent upstream as `X-API-Key` on every Gorelo call. Scoped keys that lack access to an endpoint get Gorelo's own `403`, surfaced as `unauthorized`. |
| `X-Gorelo-Region` | Yes | `us` or `au` — selects the regional API host (`https://api.usw.gorelo.io` / `https://api.aue.gorelo.io`). Any other value is a `401` naming the two accepted values (same "missing/invalid header → 401 naming what's expected" pattern as every sibling connector, SOP §3.2). |

A request to `/mcp` missing either header gets `401` listing what's missing (AC11). Credentials are
never cached or shared across requests (SOP §3.3/3.4) — the two headers are read into a
`ContextVar` per request and reset in `finally`.

**Tools** (17 total, within the SOP §A4 ceiling of 20; `write` tools are not `readOnlyHint`):

| Area | Tools |
|---|---|
| Tickets | `gorelo_list_tickets` (cursor, limit, status_names, priority_names, type_names, client_ids, contact_ids, lead_assignee_ids, query, updated_since/before, created_since/before), `gorelo_get_ticket` (**ticket_id**), `gorelo_list_ticket_comments` (**ticket_id**, cursor, limit, conversation_type, conversation_id); **write**: `gorelo_create_ticket` (**title**, **client_id**, **status_name_or_id**, **type_name_or_id**, **group_id**, description, contact_id, priority_name, source), `gorelo_add_ticket_comment` (**ticket_id**, **body**, conversation_id) |
| Reference | `gorelo_list_ticket_statuses`, `gorelo_list_ticket_types` (no args — resolve the tenant-specific ids AC2/AC6 need; priority is Gorelo's fixed public 0–4 scale, documented in the tool description, no lookup endpoint needed) |
| Clients | `gorelo_list_clients` (cursor, limit, status_names, query, group_ids, updated_since/before, created_since/before), `gorelo_get_client` (**client_id**) |
| Contacts | `gorelo_list_contacts` (cursor, limit, client_ids, status_names, query, updated_since/before, created_since/before), `gorelo_get_contact` (**contact_id**) |
| Contracts | `gorelo_list_contracts` (cursor, limit, client_ids, status_names, query), `gorelo_get_contract` (**contract_id**) |
| Time | `gorelo_list_time_entries` (cursor, limit, client_ids, ticket_ids, user_ids, started_since/before); **write**: `gorelo_log_time_entry` (**ticket_id**, **started_on**, **ended_on or actual_hours**, comment, billable_status, user_id) |
| Assets | `gorelo_list_agent_assets` (cursor, limit, status_names, client_ids, query), `gorelo_get_agent_asset` (**agent_asset_id**) |

Naming follows SOP §A4 (`gorelo_<verb>_<resource>`, matching `kaseya-bms-mcp`'s convention, not
`halopsa-mcp`'s area-first naming — Halo's is a documented legacy-compatibility exception, not the
default this ticket should copy). Bold parameters are required.

**Pagination** — Gorelo's own API is **cursor-based** (`Cursor`/`PageSize` request params;
`{Data: [...], DataContext: {NextCursor, PreviousCursor, HasMore, TotalCount}}` response, per the
fetched OpenAPI's `PaginatedResponse`/`*ListBaseResponse` schemas), unlike `kaseya-bms-mcp`'s
offset `top`/`skip`. Every list tool here returns:

```json
{"items": [...], "has_more": true, "next_cursor": "opaque-token", "total_count": 142}
```

`limit` maps to Gorelo's `PageSize` (default 50, max 200 — Gorelo rejects out-of-range rather than
clamping it, so the tool does the same and surfaces `invalid_argument`); `cursor` maps to `Cursor`
and must be passed back exactly as received (opaque to the caller). A result over 20,000 characters
serialized is truncated with `"truncated": true` and the same `next_cursor` still applies, per SOP
§A4's token-economy rule.

**Create ticket** (`POST /v1/tickets`, body `CreateTicketCommand`) — required fields `Title`
(≤250 chars), `StatusId`, `TypeId`, `GroupId`; `ClientId`/`ContactId`/`PriorityId` (fixed 0–4 scale:
None=0, Urgent=1, High=2, Normal=3, Low=4) optional. `gorelo_create_ticket` accepts
`status_name_or_id`/`type_name_or_id` (resolved via `gorelo_list_ticket_statuses`/
`_types` the same way `kaseya_bms_create_ticket` resolves status/priority names) and a
`priority_name` (`none|urgent|high|normal|low`, case-insensitive) mapped to the fixed scale
directly — no lookup call needed for priority.

**Add ticket comment** (`POST /v1/tickets/{id}/comments`, body `CreateCommentCommand`) — required
`ConversationTypeId` (1 Public, 2 Private, 3 Side Conversation, 4 Approval) and `Body` (HTML;
plain text is accepted and not escaped specially, matching Gorelo's own "text without markup is
wrapped in a paragraph" behavior). `gorelo_add_ticket_comment` defaults `conversation_type` to
Public (1) when no `conversation_id` is given (AC5); `ConversationId` is required by Gorelo for
Side Conversation/Approval and the tool surfaces Gorelo's own validation error as
`invalid_argument` if omitted for those two kinds.

**Log time entry** (`POST /v1/time-entries`, body `CreateTimeEntryCommand`) — required `TicketId`
(xor `TaskId`, v1 only supports the ticket form) and `StartedOn`, plus **either** `EndedOn` or
`ActualHours` (Gorelo computes the one not given) — `gorelo_log_time_entry` enforces "exactly one
of `ended_on`/`actual_hours`" client-side before calling Gorelo (AC9), returning `invalid_argument`
on neither/both rather than forwarding an ambiguous request upstream.

**Error envelope** — every tool returns a JSON string; failures use:

```json
{"error": {"code": "unauthorized", "message": "Gorelo returned HTTP 403 for GET v1/tickets: <Message> (code <6-digit Error.Code>)", "retryable": false}}
```

| Gorelo HTTP status | `code` | `retryable` |
|---|---|---|
| 400 | `invalid_argument` | false |
| 401 | `unauthorized` | false |
| 403 | `unauthorized` | false |
| 404 | `not_found` | false |
| 409 | `invalid_argument` | false |
| 429 | `rate_limited` | true (after the client's own bounded retries are exhausted) |
| 5xx / network error | `upstream_error` | true |

Gorelo's own response carries a `Notifications` array of `{Code, Message, PropertyName, ActionHint,
DocUrl}` (fetched from the OpenAPI `Error` schema) even inside an `IsSuccess: true` envelope for
some partial-failure cases (per its `*ListBaseResponse` shape) — the client treats a non-empty
`Notifications` array alongside `IsSuccess: false` as an upstream error using the same mapping
table, not only non-2xx HTTP statuses.

**Backward compatibility**: not applicable — first version of a new connector, no existing
`tools/list` contract to preserve (contrast with `kaseya-bms-mcp` AC9-style regression
requirements, which only apply once a connector is already deployed).

### Key flow / sequence

```
Agent -> MCP Gateway -> gorelo-mcp (POST /mcp, X-Gorelo-Api-Key + X-Gorelo-Region in headers)
  -> middleware: read + validate headers -> ContextVar, else 401
  -> tool handler (e.g. gorelo_list_tickets):
       resolve any status_names/priority_names/type_names via lookup tools or the fixed scale
       -> api_client.get("/v1/tickets", params={StatusIds, PriorityIds, ..., Cursor, PageSize})
            -> httpx request to https://api.{usw|aue}.gorelo.io/v1/tickets, header X-API-Key
            -> 2xx: shape Data[] + DataContext into {items, has_more, next_cursor, total_count}
            -> non-2xx or IsSuccess:false: map status/Notifications -> {error:{code,message,retryable}}
  -> ContextVar reset in finally
  -> response serialized compact (ensure_ascii=False, no indent), truncated at 20,000 chars if needed
```

### Non-functional

- **Idempotency & concurrency**: reads are naturally idempotent. `gorelo_create_ticket` and
  `gorelo_log_time_entry` are not idempotent by design (Gorelo's API has no client-supplied
  idempotency key) — calling twice creates two records; this matches every sibling connector's
  `create_ticket` tool and is documented in the tool description, not solved in this repo.
  One `httpx.AsyncClient` per request (SOP §3.3) — no shared connection state leaking between
  concurrent tenants' requests.
- **Performance**: `limit` capped at 200 (Gorelo's own hard cap), default 50; no unbounded list
  call is possible. Outbound timeout 5s connect / 30s read; bounded retry with backoff on 429/5xx,
  respecting `Retry-After` when Gorelo sends it; a single tool call's total retry budget stays
  under 120s (SOP §5).
- **Security**: `X-Gorelo-Api-Key` only ever read from the request header, never logged, never
  written to disk or env; Gorelo's own per-key scoping (e.g. a Documents-only key cannot reach
  Tickets) is the vendor's own access boundary and is preserved end-to-end — this connector adds
  no broader access than the key itself already grants. `gitleaks detect` run before delivery
  (SOP §0.4/§11) to confirm no credential or example key is committed.
  **Prompt-injection surface**: ticket titles/descriptions/comments are free text written by end
  customers and returned verbatim to the agent — this is the same shape every ticketing-system
  connector has (HaloPSA, Kaseya BMS) and is mitigated at the gateway layer (SOP's "vendor
  responses are scanned for prompt-injection patterns" — see `reference/readme-connector-
  section.md`), not re-implemented per-connector.
- **Multi-tenant isolation**: the service itself is single-tenant-per-request and stateless — the
  only "tenant" dimension is which Gorelo service-provider account the caller's API key belongs
  to, and Gorelo's own API already scopes every endpoint to the key's own service provider (no
  cross-service-provider query is possible through this API). No local caching of any tenant's
  data between requests.
- **Observability**: structured log line per tool call (tool name, Gorelo HTTP status, `code` on
  failure) with the API key redacted; `/health` is a local-only probe (SOP §1.1) so an outage of
  Gorelo itself does not flip this service's health check.

### Rollout & rollback

No feature flag — this is the first version of a new connector; it does not exist on the platform
today, so there is nothing to gradually roll out to. Rollout is: merge to `main` → `/api/vendor-
register` (new vendor, not yet known to the MCP gateway) → health check passes → connector
becomes available to any tenant that chooses to connect it (opt-in per tenant, same as every other
connector — see the "Connector detail view" product fact, `wiki: ProductDocs/15-Capabilities.md §
Connector detail view — new at v4.1.490`, `_verified_` 2026-08-27/2026-08-31). Rollback is: no
tenant can be using it before the first `vendor-register` succeeds, so "rollback" only matters
after that point and means reverting `main` and re-publishing — no data migration exists to reverse
since this connector stores nothing itself.

## Decisions made by DEV01

(Per `mcp-track.md` 2.4 — choices made with no one to ask, each posted in a separate
`[DESIGN DECISIONS]` comment after the `[DESIGN]` stub.)

- **17-tool v1 scope (tickets, reference lookups, clients, contacts, contracts, time entries,
  assets) rather than Gorelo's full 174-operation surface or the open-source reference's 112
  tools** — why: SOP §A4 caps a single service at ≤20 tools and requires merging/trimming to
  "capabilities an agent would actually want", not an API mirror; this set matches what the two
  existing sibling PSA connectors (Kaseya BMS, HaloPSA) ship as their core, and covers exactly what
  "give an AI live access to a PSA" means in practice (service desk + CRM + billing-adjacent +
  time + device inventory). Alternative not chosen: port the open-source reference's full 112-tool
  surface — rejected both because it is forbidden by SOP (no porting third-party MCP code) and
  because it is nearly 6x the tool ceiling.
- **No destructive (DELETE) tools in v1** — why: SOP defaults new tools to read-only and none of
  delete-ticket/delete-client/delete-contract/delete-time-entry has a stated need in this ticket.
  Alternative: include deletes behind an env-gate the way the open-source reference does
  (`GORELO_ENABLE_DESTRUCTIVE`) — not chosen for v1 to keep the first version's blast radius small;
  can be added later as a scoped follow-up if a real need appears.
- **Region selected via an explicit `X-Gorelo-Region` header (`us`/`au`) rather than inferred from
  the API key** — why: Gorelo publishes two entirely separate regional hosts with separate Swagger
  docs and no documented single global entry point; explicit is safer than guessing and fails
  loudly (`401` naming the two accepted values) rather than silently hitting the wrong region.
  Alternative: default to `us` when the header is omitted — not chosen because a silent wrong
  default risks a confusing `401`/`403` with no indication *why*, worse than requiring the header.
- **Cursor pagination surfaced to the agent as `{items, has_more, next_cursor, total_count}`
  instead of translating Gorelo's cursor into a synthetic offset (`skip`) to match
  `kaseya-bms-mcp`'s shape** — why: Gorelo's cursor is explicitly opaque (not reconstructible from
  an offset), and `halopsa-mcp`'s README already documents a `next_offset`-only approach as
  specific to HaloPSA's own offset API — there is no single "house pagination shape" to match
  exactly; following Gorelo's own actual mechanism is safer than building a leaky abstraction over
  it. Alternative: emulate `top`/`skip` with an internal cursor cache — not chosen because it would
  require server-side state, violating the "truly stateless" requirement (SOP §1.3).

### Design corrections found while building against the live OpenAPI document

The design (`docs/tickets/PRD-21211.md` Tech design / Decisions sections) was written from the
same OpenAPI document but at the prose level; three points needed a small, behavior-preserving
correction once the exact schema was implemented against:

1. **Ticket priority does have a lookup endpoint.** `GET /v1/tickets/priorities` exists (returns
   the same `{Id, Name}` shape as `/statuses`/`/types`) even though the design assumed a hardcoded
   0-4 scale with no lookup call. `gorelo_list_tickets`'s `priority_names` and
   `gorelo_create_ticket`'s `priority_name` both resolve through this lookup now, consistent with
   how status/type names resolve — the write-side fixed enum (`None`=0..`Low`=4) is unchanged.
2. **No status-name lookup for clients, contacts, contracts or assets.** Confirmed against the
   live spec: unlike tickets, Gorelo has no `/statuses` endpoint for these four areas. Their list
   tools take `status_ids` (numeric) instead of `status_names` — the design's table listed
   `status_names` for `gorelo_list_clients`/`_contacts`, but no AC or test case in this ticket
   actually requires resolving a client/contact/asset status name, so this is a signature detail,
   not a capability loss.
3. **`gorelo_add_ticket_comment` needs a `ConversationTypeId` that matches the target
   conversation**, not just a `ConversationId`; Gorelo rejects `ConversationId` on the Public/
   Private types. The tool sends `1` (Public) when no `conversation_id` is given and `3` (Side
   Conversation) when one is — matching TC-GORELO-006/007 exactly. Approval conversations (`4`)
   are out of scope for this tool (documented in its description) since no AC or test case asks
   for them.
4. `gorelo_create_ticket`'s `POST /v1/tickets` only returns the new ticket's `Id`; the tool makes
   one extra `GET` immediately after to return `display_number` alongside it, since AC6 asks for
   both.

None of these change the product-level behavior committed to in the AC/test cases — each is
documented above and in the README's Delivery notes.
